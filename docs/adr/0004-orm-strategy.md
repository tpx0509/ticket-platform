# ADR-0004 数据访问采用 Prisma 与原生 SQL 双轨

日期：2026-11-02
状态：已采纳

## 背景

需要选一个数据访问层。常规的增删改查希望有类型安全和自动补全；向量检索、复杂聚合、批量统计则天然是 SQL 的领域。少数 ORM 能同时做好这两件事。

## 决策

- **常规 CRUD 用 Prisma**：单表与简单关联的读写、迁移管理、类型生成。
- **原生 SQL 用 `$queryRaw`**：pgvector 相似度检索、多表聚合统计、`INSERT ... SELECT` 类批量操作、需要精确控制索引命中的查询。
- 原生 SQL 一律参数化（`Prisma.sql` 模板），禁止字符串拼接。
- 迁移只由 Prisma Migrate 管理。`vector` 类型用 `Unsupported("vector(1024)")` 声明，保证迁移能生成，读写走原生 SQL。

## 备选方案

**A. 全用 Prisma。** 一致性好，但 pgvector 的 `<=>` 距离算子、HNSW 索引、`to_tsvector` 全文搜索都无法通过 Prisma Client 表达。硬要用只能先全表拉出来在内存里算——数据量一涨就是灾难。

**B. 全用原生 SQL（配 Kysely 或 Drizzle）。** 类型安全也好，SQL 掌控力强。但迁移工具与生态成熟度不如 Prisma，且 NestJS 生态里的示例与最佳实践大多围绕 Prisma。切换成本主要在团队协作而非个人使用。

**C. TypeORM。** NestJS 官方文档首选，但装饰器实体与迁移的坑较多，类型推导在复杂关联下会退化。

## 理由

1. 承认两类查询本质不同：一类是"取几条记录"，一类是"让数据库用索引做计算"。用同一套抽象硬套，后者必然写得很别扭。
2. Prisma 的迁移是整个项目唯一的结构变更入口，这点比它的查询能力更重要。
3. 原生 SQL 集中在少数几个 repository 方法里，边界清晰：`kb/search.repository.ts`、`tickets/stats.repository.ts`。不是"哪里方便哪里写 SQL"。
4. 能讲清"什么时候不该用 ORM"，本身就是工程判断力的体现——这比会用一个工具更有价值。

## 后果

- 原生 SQL 的返回类型需要手工声明 interface，并用 `$queryRaw<T>` 标注。类型安全在这一层由开发者保证，编译器帮不上忙。
- 原生 SQL 必须写集成测试。它不经过 Prisma 的类型检查，字段改名后只有运行期才会暴露。
- `Unsupported` 字段在 Prisma Client 里不可读写，任何需要 `embedding` 的地方都必须走原生 SQL。这是刻意的：避免有人在循环里逐条读向量。
- 团队需要同时熟悉两套写法。用目录结构和评审规则把边界固定下来，避免演变成"到处都是 SQL"。
