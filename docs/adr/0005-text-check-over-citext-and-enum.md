# ADR-0005　枚举用 text + CHECK，大小写不敏感靠归一化

状态：已采纳（2026-11-03）

## 背景

数据模型最初规划用 `citext` 存邮箱、用 PG `enum` 类型存角色与状态。落地时遇到两个硬约束：

1. **Prisma 无法表达 `citext`。** 客户端类型映射里没有这个原生类型，只能用 `Unsupported("citext")` 声明，而一旦声明为 Unsupported，字段就从 Prisma Client 里消失，`findUnique({ email })` 直接不可用。若在 schema 里写成 `String`，数据库实际是 `citext`，每次 `migrate dev` 都会检测到类型漂移并要求改回 `text`。
2. **PG `enum` 的变更成本高于收益。** 加一个枚举值需要 `ALTER TYPE ... ADD VALUE`，该语句在事务里限制多；删除或重命名一个值几乎等于重建类型。角色这类"业务上一定会加值"的字段，用 enum 是把将来的迁移成本提前锁定。

## 备选方案

| 方案 | 否决原因 |
|---|---|
| 继续用 `citext`，Prisma 侧声明为 `Unsupported` | 字段直接从客户端消失，邮箱查询只能手写 SQL，等于放弃 ORM 的核心价值 |
| 用 `citext`，每次迁移后手工修掉漂移 | 漂移检测会一直报警，每次 `migrate dev` 都要人工介入，团队协作必然出错 |
| 邮箱用 `text` 加函数唯一索引 `lower(email)` | 可行，但会与 `@unique` 并存，多维护一个索引；且仍挡不住写入大写值 |
| 角色用 PG `enum` | 加值要 `ALTER TYPE`，且历史迁移重放风险高，收益不抵成本 |

## 决定

- 邮箱、slug 等需要大小写不敏感的字段用 `text`，**写入前统一转小写**，并在数据库层加 `CHECK (column = lower(column))`。配合原有的唯一索引，效果与 `citext` 等价：任何绕过应用层写入大写值的行为都会被数据库拒绝。
- 角色、状态、优先级等枚举字段用 `text` + `CHECK (... IN (...))`，约束显式命名（`<table>_<column>_ck`），改约束就是一条普通 `ALTER TABLE`。

## 后果

- 收益：ORM 与数据库一致，无类型漂移；枚举变更是一次普通迁移；约束名字可读，报错直接指向规则。
- 代价：大小写不敏感的保证从"类型层面"降级为"写入约定 + CHECK"。任何新写入路径（导入脚本、后台修数、其他服务）都必须遵守归一化约定，否则会撞上 CHECK 而失败。这是显式失败，好过静默产生重复账号。
- 查询侧注意：不要写 `where email = 'Foo@x.com'`，必须先 `toLowerCase()`。这一条要写进代码评审清单。
