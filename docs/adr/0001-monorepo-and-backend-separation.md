# ADR-0001 前后端分离 + monorepo

日期：2026-11-02
状态：已采纳

## 背景

需要决定两件事：前端与后端是合成一个 Next.js 应用（Route Handler / Server Action 承载接口），还是拆成独立服务；以及代码放一个仓库还是多个。

## 决策

前端 `apps/web`（Next.js，仅 UI 与 SSR）与后端 `apps/api`（NestJS，独立进程、独立端口）分离部署，通过 HTTP 通信。代码放同一个 pnpm workspace 仓库，共享 `packages/shared`。

## 备选方案

**A. Next.js 全栈单应用。** 开发最快，部署最简单，一个进程搞定。但接口逻辑与渲染逻辑耦合在同一个运行环境，无法独立扩容、独立发布、独立限流；分层只能靠自觉，随着功能增加必然退化成"页面里写 SQL"。

**B. 后端 + 多个前端仓库。** 边界最清晰，适合多端（Web、小程序、App）。但当前只有一个前端，多仓库会让契约同步变成手工操作。

## 理由

1. **部署与故障隔离。** 接口被刷爆时，页面仍能正常打开并显示错误；反过来改前端样式不需要动接口服务。单应用做不到这一点。
2. **分层是被结构强制的，不是被纪律要求的。** 独立服务里，controller / service / repository 是目录结构的一部分；Next.js 里一个文件既可以是页面也可以是接口，边界靠人守，守不住。
3. **monorepo 解决契约同步。** 类型定义只有一份，前端 `import` 后端同一份 DTO。接口改字段，前端在编译期报错，而不是上线后发现字段是 `undefined`。这是拆两个仓库做不到的。
4. **monorepo 不牺牲部署独立性。** pnpm workspace 只是开发期结构，构建产物仍是独立镜像，可以分别部署、分别回滚。

## 后果

- 本地开发需要同时起两个进程；用 `pnpm dev` 并行启动解决。
- 跨域需要配置。开发期由 Next.js rewrites 代理到 API，生产由 Nginx 统一入口，避免前端代码里出现环境相关的基地址。
- 每个应用需要独立的 Dockerfile 与 CI 任务。
- `packages/shared` 增加了一次构建：改共享类型后需要重新构建依赖它的应用。用 workspace 协议（`"@ticket/shared": "workspace:*"`）配合 `tsc --watch` 缓解。
