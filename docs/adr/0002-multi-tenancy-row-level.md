# ADR-0002 多租户采用行级隔离 + 行级安全策略

日期：2026-11-02
状态：已采纳

## 背景

平台服务多个组织，组织之间的数据必须互不可见。这是整个系统最不能出错的地方——一次越权读取，等于把所有客户的数据泄露给其中一个客户。

## 决策

- 采用**共享库、共享表、行级隔离**：所有业务表带 `org_id`，每个查询显式带租户条件。
- 追加**数据库行级安全策略（RLS）作为第二道防线**：应用连接使用受限角色，策略强制 `org_id = current_setting('app.org_id')::uuid`。
- 每个请求在进入事务时执行 `SET LOCAL app.org_id = '<当前组织>'`。用 `SET LOCAL` 而非 `SET`，保证设置随事务结束自动失效，不会因为连接池复用而串租户。

## 备选方案

**A. 每个租户一个 schema。** 隔离强，但迁移要在 N 个 schema 上跑 N 次，Prisma 对动态 schema 支持很差，备份恢复也复杂。租户数上百后运维成本不可接受。

**B. 每个租户一个数据库。** 隔离最强，适合金融与强合规场景。但连接数、迁移、成本都随租户数线性增长，且跨租户统计需要额外设施。当前规模属于过度设计。

**C. 只做应用层过滤，不加 RLS。** 实现最省事。但代价是：任何一个开发者漏写一个 `where org_id`，就是一次数据泄露，而这类遗漏在代码评审里极难发现——查询看起来完全正常。

## 理由

1. 行级隔离在租户数量增长时的成本几乎不变，是 SaaS 的事实标准。
2. RLS 把"记得加租户条件"从人的纪律变成数据库的强制约束。漏写 `where` 时，查询返回空集而不是别人的数据——错误的失败方式从"泄露"变成"查不到"，这是本质区别。
3. `SET LOCAL` + 事务绑定，避免了连接池复用导致的租户上下文串号。这是行级隔离方案里最容易踩的坑。
4. 索引上把 `org_id` 放在复合索引首列，租户条件同时也是索引条件，隔离不带来额外性能代价。

## 后果

- 所有业务表必须有 `org_id` 且非空。跨组织的全局实体（如 `users`）例外，通过 `memberships` 关联。
- 连接池里应用使用的数据库角色不能是超级用户，否则 RLS 被绕过。需要单独建角色并只授予 DML 权限。
- 后台任务（worker）没有 HTTP 请求上下文，必须显式传入并设置 `org_id`。任务结构里要带租户标识。
- 跨租户的运维查询（如平台总单量）需要另建只读角色或走独立连接，不能复用应用连接。
- 迁移脚本执行时需要绕过 RLS，走所有者角色。

## 验证方式

编写越权测试用例：以 A 组织成员身份请求 B 组织的工单详情，必须返回 404。该用例进 CI，任何改动导致它失败都阻断合并。
